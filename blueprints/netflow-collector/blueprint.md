## 1. Project Overview & Non-Goals

### Vision

NetFlow Collector is a single-binary Go daemon that receives NetFlow v5/v9/IPFIX flow records from
network exporters, batches them, and writes them into a pluggable storage backend, where a small REST
query layer makes them answerable by Grafana, `curl`, or an SRE's own script. It is built for a
network that has hundreds of routers and a medium data centre's worth of traffic — order-of-magnitude
tens of thousands of flow records per second — and for a freshness target measured in minutes, not
hours.

The point of the project is the **architecture**, stated by its author as the primary goal: two
boundaries — input sources and storage backends — are genuine interfaces with two independent
implementations each in v1, so that adding a third is a contained change rather than a fork. A
storage backend is a `Sink` plus a `Querier`, nothing more; an input is a `Source`, nothing more.
Neither interface knows that packets arrive over a network or that rows land in SQL. That is what
makes a future database-import adapter, or a columnar backend, a drop-in rather than a rewrite. This
is not a claim about elegance for its own sake: it is the difference between "we also support
MariaDB" being a weekend and being a quarter.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| Network engineer | Point routers at the collector, then answer "who talked to whom, when, how much" over a time range | daily |
| SRE / on-call | Check that ingest is still flowing, that drops are zero, and that a sink has not fallen behind | daily, and during incidents |
| Platform engineer extending the project | Add a new storage backend or a new input source without touching the pipeline | once per backend |

### Goals — v1 scope

1. Ingest NetFlow v5, v9 and IPFIX over UDP at tens of thousands of records per second on one
   instance, with bounded memory and an explicit, counted drop policy under overload.
2. Ingest pre-decoded flow records from a Kafka topic, with at-least-once redelivery deduplicated on
   write, proving the input boundary is pluggable rather than hypothetical.
3. Write every ingested record to one or more configured storage backends in parallel, with
   TimescaleDB and MariaDB both implemented and both passing one unmodified conformance suite.
4. Make records queryable within 1–2 minutes of arrival through a cursor-paginated REST API guarded
   by a static API key.
5. Be operable: structured JSON logs, Prometheus metrics for ingest rate, drop rate, batch-write
   latency and write errors, separate `/healthz` and `/readyz`, a container image, a CI pipeline, and
   a runbook.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| Database-import `Source` (replaying historical records from another system) | The value of v1 is proving the boundary, not filling it a third time. The `Source` interface is **designed** to accept it unchanged — `Start(ctx, chan<- FlowRecord) error` names no network type — so this is a deferral, not a design debt | An operator needs to backfill from an existing nfdump/ElastiFlow store |
| GeoIP / ASN enrichment of flow records | Needs a maintained data file, a refresh story, and a per-record lookup in the hot path — all of which change the pipeline's latency budget | Ingest is stable and someone asks a question that AS numbers alone cannot answer |
| Alerting / anomaly detection | Prometheus plus the operator's own Alertmanager already does this, and building a second rules engine competes with a better one | Never, unless flow-specific detection needs state the metrics pipeline cannot carry |
| Built-in web dashboard / UI | Grafana over the REST API or straight over TimescaleDB is strictly better than anything shipped here, and a UI would double the surface area | A user demonstrates a query shape Grafana genuinely cannot express |
| Multi-tenancy / RBAC beyond a single API key scope | The audience is the operator of the collector, not customers. A key table with issuance, scopes and rotation is `api-design.md`'s enterprise pattern and is overkill for one team | Two teams need different views of the same collector |
| Horizontal collector clustering / sharding | One instance covers the stated volume. Sharding means exporter-to-instance assignment, per-shard state, and a merge layer in the query path — a second architecture | A single instance saturates, which the §16 metrics will show before it hurts |
| Flow payload capture | NetFlow carries no payload; capturing it would be a packet-capture product with a completely different privacy posture | Never |

**The builder must not implement anything in this table**, even if it seems like a small addition
while working on an adjacent step. If a step appears to require a non-goal, that is a blueprint
defect — stop and report it rather than expanding scope.

### Success metrics

| Metric | Target | How measured |
|---|---|---|
| Sustained ingest without unaccounted loss | ≥ 20,000 records/second with `ingested + dropped == offered` exactly | `go test -tags=load -run TestPipelineLoad ./internal/pipeline/...` — step 13's gate; the measured rate is recorded in `docs/performance.md` |
| Query freshness | p95 visibility lag < 120 s | `histogram_quantile(0.95, rate(netflow_record_visibility_lag_seconds_bucket[5m]))` against `/metrics` |
| Storage boundary is real | 2 backends pass 1 unmodified conformance suite | `go test -race ./internal/sink/...` plus the step-6 gate that diffs `internal/sink/sinktest/conformance.go` against its step-4 commit |
| Input boundary is real | 2 sources satisfy `flow.Source` with no interface change | `go test -race ./internal/source/...` and the step-2 gate asserting `internal/flow/ports.go` names no `net.Conn`/`net.Addr`/`net.PacketConn` |
| Backpressure is counted, never silent | Under forced overload, drops are non-zero, bounded, and every offered record is accounted for | step 3's and step 13's conservation assertions |

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime | Go, single static binary (`CGO_ENABLED=0`) | Goroutine-per-connection costs kilobytes; memory stays flat in a long-running ingest daemon; one file deploys anywhere. | Styling | NOT APPLICABLE — headless daemon, no UI in v1 | — |
| Component layer | NOT APPLICABLE — headless daemon, no UI in v1 | — |
| Database | PostgreSQL + TimescaleDB (default) and MariaDB (second implementation) | Timescale gives time partitioning, compression and retention as a policy rather than as code, which is exactly what an append-only flow table needs. MariaDB exists to prove the `Sink`/`Querier` interfaces are not secretly Postgres-shaped — it is a conformance instrument as much as a feature |

| Auth | Single-scope static API keys from `NFC_API_KEYS`, constant-time compared in middleware on `/v1/*` | The audience is one operations team. `api-design.md`'s `api_key` table with issuance, hashing, scopes and rotation is the enterprise pattern and is a deliberate deviation downward — named in §8 with the v2 upgrade path |
| Background work | None. The daemon *is* the long-running process | A queue would be a second delivery guarantee on top of UDP's none and Kafka's at-least-once. The bounded channel plus batcher is the whole scheduler |
| Payments | NOT APPLICABLE — infrastructure software, no billing surface | — |
| File storage | NOT APPLICABLE — all state is in the storage backends | — |
| Email / notifications | NOT APPLICABLE — alerting is the operator's Alertmanager (§1 Non-Goals) | — |
| Hosting | Operator-run container (Docker Compose in v1), behind the operator's existing ingress | A PaaS is the wrong shape: this binds a privileged UDP port, needs a persistent process, and lives next to the routers that export to it. `deployment.md`'s "long-lived process design + request-scoped host" row is precisely the combination being avoided |
| Package manager | `go` modules, with build-time tools as `go tool` directives in `go.mod` | One manifest, one lockfile (`go.sum`), and `go tool golangci-lint` runs the pinned linter with nothing installed globally |

**Boundary rules**

- `internal/flow` imports **nothing** from this module. It is the contract both boundaries are
  written against, and anything it imports becomes part of that contract.
- `internal/flow/ports.go` names no `net.Conn`, `net.Addr` or `net.PacketConn`. A `Source` that reads
  from a database, a file, or a test fixture must be able to satisfy the interface without pretending
  to be a socket. Step 2's `Verify` enforces this mechanically.
- `internal/pipeline` imports `internal/flow` and `internal/obs` only. It never imports a concrete
  source or a concrete sink — it is handed `[]flow.Source` and `[]flow.Sink` by `internal/app`.
- `internal/sink/*` and `internal/source/*` never import each other, and never import
  `internal/pipeline` or `internal/api`.
- `internal/api` depends on `flow.Querier`, never on a concrete backend package.
- `internal/app` is the only package that constructs concrete types. It is the wiring layer and the
  only place `NFC_SOURCES` and `NFC_SINKS` are turned into implementations.
- Only `internal/config` reads `os.Getenv`. Everything else takes a typed `config.Config` field.
- Soft cap of 300 lines per file (Go track convention). Split by responsibility, not by type.

**Resolution convention.** Every internal package is imported by its full module path
`github.com/bogie5464/netflow-collector/internal/<pkg>`; there are no path aliases, no `pkg/`, and no
relative imports. Embedded assets are addressed relative to the directory of the file carrying the
`//go:embed` directive. Both halves are reconciled against every loader in §19.6's *Resolution
convention matrix* — which is why `migrations/embed.go` sits at the root of `migrations/` and not
inside `internal/sink/*`.

**Module path.** `github.com/bogie5464/netflow-collector` is a concrete choice, not a placeholder; no
GitHub organisation was specified. Renaming it is two commands and is documented in `README.md`
(step 12): `go mod edit -module github.com/<org>/netflow-collector` followed by a find/replace of the
old import prefix across `cmd/`, `internal/` and `migrations/`.

**Every output path drawn in this tree is a value some emitted config also states.** `bin/collector`,
`/usr/local/bin/collector`, `docs/openapi.json`, `blueprints/` and the three service ports are all
reconciled once in §19.6's *Cross-artifact value reconciliation* table; this tree takes the literal
strings from there.

**A tree entry is documentation. Drawing a file here does not create it.** Every file above has one
of two origins: a §9 step authors it (named in that step's **Do** list and in its `tasks.json`
`files` array), or it is emitted as a real file under `workspace/` (§19.6) and lands via the single
guarded copy §10's Bootstrap runs before step 1. `go.mod` and `go.sum` have a third, explicitly
stated origin: the `go mod init` and `go get` commands in §10 Bootstrap. They are **not** emitted
under `workspace/`, which is what keeps the re-runnable copy from ever reverting them.

## 4. Data Model

Adapted from `knowledge/capabilities/database.md`. Two of its defaults are deliberately **not**
applied, each for a reason that file itself gives:

- **No soft delete on `flow_records`.** `database.md` exempts "logs, events, sessions, and
  high-volume append-only tables" from soft deletion and says to delete or partition instead.
  Retention here is a Timescale partition-drop policy, not a `deleted_at` column that every query
  must remember to filter.
- **No raw/staging/marts zoning.** That is the batch-ETL pattern in
  `knowledge/shapes/data-pipeline-analytics.md`, and it does not fit a streaming daemon.
  `flow_records` is a single append-only fact table with time-based partitioning. There is no
  transform stage to rebuild from.

One more deliberate absence: there is **no `pipeline_run` / `data_quality_result` table**. Those
belong to a scheduled DAG. A long-running daemon's operational state is Prometheus counters and
gauges (§16), which are cheaper, higher-resolution, and already what the on-call engineer looks at.

### Entities

**`exporters`** — one row per device that has ever sent this collector a flow record. Created on
first sight by the sink, never deleted by the application.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | bigint | PK, generated always as identity (pg) / auto_increment (mariadb) | Internal surrogate key. Referenced by `flow_records.exporter_id`; never appears in a URL |
| `ip_address` | inet (pg) / varbinary(16) (mariadb) | not null, unique | The source address of the exporting device. Unique index is what makes first-sight upsert race-free |
| `first_seen_at` | timestamptz (pg) / datetime(6) (mariadb) | not null | Set once on insert |
| `last_seen_at` | timestamptz / datetime(6) | not null | Advanced at most once per batch per exporter, not per record — a per-record update would be the hottest write in the system |
| `label` | text / varchar(255) | nullable | Operator-assigned human name. The only column a human ever writes |
| `created_at` | timestamptz / datetime(6) | not null, default now | `database.md`'s required column |
| `updated_at` | timestamptz / datetime(6) | not null, default now | Maintained by a trigger on Postgres, by `ON UPDATE CURRENT_TIMESTAMP(6)` on MariaDB — never by application code |

**`flow_records`** — one row per flow record received. Append-only. Partitioned by `received_at`
(Timescale hypertable on Postgres; unpartitioned on MariaDB in v1 — see *Retention* below).

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `received_at` | timestamptz / datetime(6) | not null, partition key | When **this collector** accepted the record. On the Kafka path it is taken from the message, never from the consumer's clock — that is what makes redelivery dedup possible (see *Deduplication*) |
| `seq` | bigint | identity / auto_increment | Monotonic tie-breaker. Not a public id: it exists so cursor pagination is stable when two records share a `received_at` |
| `exporter_id` | bigint | not null, FK → `exporters.id` | Resolved by the sink from `FlowRecord.ExporterAddr` through a bounded in-memory cache |
| `flow_type` | text / varchar(16) | not null, one of `netflow5`, `netflow9`, `ipfix` | A constrained text column, not a database enum — `database.md`: enum types are painful to alter |
| `first_switched` | timestamptz / datetime(6) | not null | Start of the flow, as reported by the exporter. Not the same clock as `received_at` |
| `last_switched` | timestamptz / datetime(6) | not null | End of the flow, as reported by the exporter |
| `src_addr` | inet / varbinary(16) | not null | IPv4 addresses are stored as-is on Postgres and as 4-byte values on MariaDB; IPv6 as 16 bytes |
| `dst_addr` | inet / varbinary(16) | not null | |
| `src_port` | integer / smallint unsigned | not null | 0 for protocols without ports |
| `dst_port` | integer / smallint unsigned | not null | |
| `protocol` | smallint / tinyint unsigned | not null | IANA protocol number: 6 TCP, 17 UDP, 1 ICMP |
| `tcp_flags` | smallint / tinyint unsigned | not null, default 0 | Cumulative OR of flags seen in the flow |
| `packets` | bigint | not null | Packet count **before** sampling correction. Multiply by `sampling_rate` to estimate the wire count |
| `bytes` | bigint | not null | Octet count before sampling correction, same caveat |
| `sampling_rate` | integer | not null, default 1 | 1 means unsampled. Storing it per row is what makes a mixed fleet answerable |
| `input_iface` | integer | not null, default 0 | SNMP ifIndex on the exporter |
| `output_iface` | integer | not null, default 0 | |
| `src_as` | integer | not null, default 0 | 0 means "the exporter did not tell us" |
| `dst_as` | integer | not null, default 0 | |
| `next_hop` | inet / varbinary(16) | nullable | Null when the exporter omits it |
| `dedup_key` | bytea / varbinary(16) | **nullable** | **This nullability is the whole dedup design.** Non-null on Kafka-sourced rows, null on UDP-sourced rows. See below |

There is deliberately no `id uuid` on `flow_records`. Flow records are never addressed individually:
the only access pattern is a range plus filters, so a per-row UUID would cost 16 bytes and an index
on every one of billions of rows to serve a URL shape this API does not have.

### Deduplication — two paths, one table, no branching in the sink

NetFlow over UDP is best-effort by design. Packet loss is normal, there is no retransmission in the
protocol, and this system does not try to recover it. Duplicates on that path are not expected, and
paying for dedup there would cost a unique-index write on every one of tens of thousands of rows per
second to prevent something that does not happen.

Kafka is different: at-least-once redelivery is normal and expected.

The reconciliation is a **nullable `dedup_key`**:

- The **Kafka** source computes `dedup_key` as a 16-byte digest of
  `(exporter_addr, first_switched, src_addr, dst_addr, src_port, dst_port, protocol)` — the natural
  key — and sets `received_at` from the message rather than the consumer's clock.
- The **NetFlow UDP** source leaves `dedup_key` nil.
- Both backends carry `UNIQUE (received_at, dedup_key)`. **In both PostgreSQL and MariaDB, NULLs in
  a unique index are distinct**, so UDP rows never collide with anything, and a redelivered Kafka
  message — identical natural key *and* identical `received_at` — collides with itself exactly once.
- Every write uses conflict-tolerant insert (`ON CONFLICT DO NOTHING` on Postgres, `INSERT IGNORE` on
  MariaDB), so the `Sink` implementation has **one** code path and knows nothing about which source a
  record came from. The interface stays batch-shaped.

The index includes `received_at`, which is also the Timescale partitioning column — a hypertable
requires every unique index to contain the partitioning column, and this one does by construction.

### Relationships

- `exporters` —(1:N)→ `flow_records`, via `flow_records.exporter_id`.
- **On delete: RESTRICT.** Deleting an exporter row with flow records is rejected by the database.
  Retention removes flow records by time, never by exporter, and an exporter row is ~100 bytes that
  nobody needs to reclaim. A cascade here would let one mistaken `DELETE FROM exporters` silently
  remove a month of traffic history.

### Indexes

| Table | Index | Why |
|---|---|---|
| `exporters` | `uq_exporters_ip_address (ip_address)` | Makes first-sight upsert race-free; also the lookup the sink's cache misses fall back to |
| `flow_records` | `idx_flow_records_exporter_received (exporter_id, received_at DESC)` | The primary query: "this exporter, this window". Equality first, then range — `database.md`'s composite ordering rule |
| `flow_records` | `idx_flow_records_received_seq (received_at DESC, seq DESC)` | The unfiltered range query and the keyset cursor predicate `(received_at, seq) < (?, ?)` |
| `flow_records` | `uq_flow_records_dedup (received_at, dedup_key)` UNIQUE | Kafka redelivery dedup. Null `dedup_key` rows are distinct, so the UDP path is unaffected |
| `flow_records` | `idx_flow_records_src_addr (src_addr, received_at DESC)` | The `src_addr=` filter, which is the second-most-asked question after "this exporter" |

Every index costs write throughput on the hottest table in the system. These five are the ones §5's
route table actually needs; do not add a sixth without a query that requires it.

### Schema

Postgres / TimescaleDB — `migrations/postgres/00001_flow_schema.sql`, hand-authored (goose's
`-- +goose Up` / `-- +goose Down` annotations; **not** produced by `goose create`):

```sql
-- +goose Up
CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE TABLE IF NOT EXISTS exporters (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ip_address    inet        NOT NULL,
    first_seen_at timestamptz NOT NULL DEFAULT now(),
    last_seen_at  timestamptz NOT NULL DEFAULT now(),
    label         text,
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_exporters_ip_address ON exporters (ip_address);

CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_exporters_updated_at ON exporters;
CREATE TRIGGER trg_exporters_updated_at BEFORE UPDATE ON exporters
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TABLE IF NOT EXISTS flow_records (
    received_at    timestamptz NOT NULL,
```

**Timestamp precision is a portability contract, not an implementation detail.** PostgreSQL
`timestamptz` and MariaDB `DATETIME(6)` both store microseconds. Go's `time.Time` carries
nanoseconds. Every `FlowRecord` timestamp is therefore truncated to microseconds — by the sink on
write, and by the conformance suite's fixtures before comparison. Skipping this is the most likely
way to make step 4's round-trip assertion fail on a correct implementation.

**MariaDB stores no timezone.** Every value is written and read as UTC, and the DSN carries
`parseTime=true&loc=UTC` so the driver does not reinterpret it in the process's local zone.

### Migrations

`github.com/pressly/goose/v3`, driven **programmatically** through its Go API, not through a CLI:

- `migrations/embed.go` declares `package migrations` and `//go:embed postgres mariadb`. The
  directive cannot reference a parent directory, which is exactly why that file lives at the root of
  `migrations/` rather than inside `internal/sink/*` — see §19.6's resolution matrix.
- Each backend's `Migrate(ctx)` calls `goose.SetBaseFS(migrations.FS)`, selects its dialect, and runs
  `goose.UpContext` against its own subdirectory. There is one migration system per database and no
  second path: nobody edits a schema through a GUI.
- Files are numbered and hand-authored (`00001_flow_schema.sql`). They are **not** produced by
  `goose create`, so their names are chosen by this blueprint rather than invented on behalf of a
  generator — the distinction matters, and the `.claude/rules/migrations.md` rule states it.
- Migrations run at boot, before any listener binds. A migration failure exits with code 3 and the
  process serves nothing (step 5, criterion 5).
- Production rule: **forward-only, expand → migrate → contract.** A `Down` block exists for local
  teardown; it is never the production rollback plan. Dropping or renaming a column on a table this
  size is a multi-release operation, and `docs/runbook.md` says so.

### Retention

- **Postgres/Timescale:** retention is a policy, not code —
  `SELECT add_retention_policy('flow_records', drop_after => INTERVAL '30 days')`, driven by
  `NFC_RETENTION_DAYS`, applied by `Migrate` after the hypertable exists. Dropping a chunk is a
  metadata operation; a `DELETE` of a month of rows is not.
- **MariaDB:** v1 does **not** partition `flow_records`, because MariaDB's `RANGE` partitioning
  requires the partitioning expression to be part of every unique key, which would force
  `dedup_key` into the partition expression and break the Kafka dedup semantics above. Retention is a
  bounded `DELETE ... WHERE received_at < ?` executed by the backend on a ticker, in chunks. This is
  a real limitation and the reason TimescaleDB is the recommended production default; it is recorded
  in `docs/runbook.md` and in §20.3.

### Seed data

A fresh database needs **no** seed rows: `exporters` fills itself on first sight and `flow_records`
is whatever the network sent. There is no admin user and no demo tenant, because there are no
accounts (§8). What a developer needs instead of seed data is *traffic*, and that is what the
conformance suite and step 5's vertical-slice test synthesise — a NetFlow v5 datagram constructed
in Go from the field layout in step 2, not a captured binary blob. There is therefore **no seed
script and no seed command**, stated here explicitly so nobody looks for one.

## 5. API Design

Per `knowledge/capabilities/api-design.md`. REST over HTTP, plain `net/http`, no GraphQL and no tRPC:
the consumers are Grafana, `curl`, and operator scripts — external clients this project does not own,
which is exactly the row that file marks "REST".

### Conventions

- **Base path:** `/v1`. Major version in the path, per `api-design.md`. Ops endpoints (`/healthz`,
  `/readyz`, `/metrics`) sit outside it, unversioned and unauthenticated.
- **Response envelope — one shape, every endpoint, including errors.**

  Success:
  ```json
  { "data": [], "meta": { "next_cursor": "eyJ0IjoxNzU4Mjg4MDAwMDAwMDAwLCJzIjo0Mn0", "has_more": true } }
  ```
  Error:
  ```json
  { "error": { "code": "validation_error",
               "message": "end must be after start",
               "details": [ { "field": "end", "message": "must be after start" } ],
               "request_id": "req_7f3a9c21d4e0" } }
  ```
  `code` is a stable machine string clients branch on; `message` is human-facing and may change.
  `details` is present only on `validation_error`. `request_id` is on **every** error response and in
  the `X-Request-Id` header of every response, success or failure.
- **Error codes and their HTTP status:**

  | `code` | Status | When |
  |---|---|---|
  | `validation_error` | 422 | Well-formed request, semantically invalid parameter |
  | `bad_request` | 400 | Malformed query string, undecodable cursor |
  | `unauthorized` | 401 | Missing or unknown API key on a `/v1/*` route |
  | `not_found` | 404 | No route matches |
  | `method_not_allowed` | 405 | Route exists, method does not |
  | `backend_unavailable` | 503 | Every configured `Querier` failed |
  | `internal_error` | 500 | Anything unhandled. Never a 200 with an error inside |

  A 200 with `{"success": false}` is the mistake `api-design.md` calls the single most common one; it
  does not appear here.
- **Validation:** `github.com/go-playground/validator/v10` over a per-operation request struct in
  `internal/api/flows.go`. The struct's tags are the **only** description of the parameters, and the
  OpenAPI builder in `internal/api/server.go` reflects over the same struct — one source, so the
  checked-in document cannot drift from the handler.
- **Pagination:** cursor-based. `limit` defaults to 100 and is **clamped** to 1000 server-side (a
  client asking for more gets 1000, not a 422 — a cap, per `database.md`). The cursor is an opaque
  base64url encoding of `{"t": <received_at unix nanos>, "s": <seq>}`; the keyset predicate is
  `(received_at, seq) < (t, s)` with `ORDER BY received_at DESC, seq DESC`. Clients never construct
  it; `meta.next_cursor` is returned when `has_more` is true and omitted otherwise.
- **Filtering:** only the parameters in the route table below are accepted. An unknown query
  parameter is a 422 with `details` naming it — silently ignoring a typo'd filter returns a wrong
  answer that looks right, which on a traffic-analysis tool is worse than an error.
- **Idempotency:** NOT APPLICABLE — every `/v1` endpoint is a read. There are no mutating endpoints in
  v1, so there is no `Idempotency-Key` handling and no `idempotency_key` table.
- **Rate limits:** none in v1. The API is on an internal address behind the operator's ingress, the
  caller set is "our own Grafana and our own scripts", and the real protection against an expensive
  query is the server-side `limit` cap plus the mandatory bounded time range. Recorded in §20.3 with
  its reversal trigger.
- **Timestamps** are RFC 3339 / ISO-8601 in UTC, both in and out.

### Routes

| Method | Path | Description | Auth | Rate limit |
|---|---|---|---|---|
| GET | `/v1/flows` | Cursor-paginated flow records over a bounded time range, with optional filters | API key | none (v1) |
| GET | `/v1/exporters` | Every known exporter with first/last seen and label | API key | none (v1) |
| GET | `/healthz` | Liveness: the process is running. Always 200 while the process can answer | public | none |
| GET | `/readyz` | Readiness: every configured backend answered a ping | public | none |
| GET | `/metrics` | Prometheus text exposition | public | none |

`/healthz` and `/readyz` are **separate endpoints with different meanings**, per the Go track's
deployment notes: conflating them turns a database blip into a restart loop, because the orchestrator
kills a process that was merely waiting.

### Critical endpoints — full detail

#### `GET /v1/flows`

Request parameters (the struct in `internal/api/flows.go`; its `validate` tags are the contract the
OpenAPI document is generated from):

| Param | Type | Rule | On violation |
|---|---|---|---|
| `start` | RFC 3339 UTC | **required** | 422 `validation_error`, `details[0].field = "start"` |
| `end` | RFC 3339 UTC | **required**, strictly after `start` | 422, field `end`, message `must be after start` |
| `exporter_id` | integer | optional, ≥ 1 | 422, field `exporter_id` |
| `src_addr` | IP address | optional, exact match, IPv4 or IPv6 | 422, field `src_addr` |
| `dst_addr` | IP address | optional, exact match | 422, field `dst_addr` |
| `protocol` | integer | optional, 0–255 | 422, field `protocol` |
| `limit` | integer | optional, default 100, **clamped** to 1000 | never an error |
| `cursor` | opaque string | optional, from a previous `meta.next_cursor` | 400 `bad_request` if undecodable |

The range `[start, end)` is half-open and **mandatory**: there is no unbounded scan of this table

### Kafka ingest message schema

This is a wire contract, so it lives here rather than in a step. One JSON object per Kafka message,
UTF-8, no envelope:

```json
{
  "exporter_addr": "198.51.100.7",
  "flow_type": "ipfix",
  "received_at": "2026-09-19T12:00:00.123456Z",
  "first_switched": "2026-09-19T11:59:58.000000Z",
  "last_switched": "2026-09-19T11:59:59.500000Z",
  "src_addr": "203.0.113.10",
  "dst_addr": "198.51.100.200",
  "src_port": 51514,
  "dst_port": 443,
  "protocol": 6,
  "tcp_flags": 24,
  "packets": 12,
  "bytes": 9000,
  "sampling_rate": 1000,
  "input_iface": 3,
  "output_iface": 7,
  "src_as": 64500,
  "dst_as": 64501,
  "next_hop": "198.51.100.1"
}
```

Rules the consumer applies, in order: `received_at` is taken from the message; if absent, from the
Kafka record's own timestamp; **never** from the consumer's clock, because that would make a
redelivered message a different row and defeat the `(received_at, dedup_key)` uniqueness in §4.
`next_hop` may be null. Unknown fields are ignored (clients must be able to add fields). A message
that fails to decode increments `netflow_packets_decode_errors_total{source="kafka"}`, is committed
past, and does not stop the consumer — one poison message must not wedge ingestion.

### Process exit codes

The binary's exit codes are a public interface — the container healthcheck, the CI gates and several
§9 `Verify` commands assert specific values, so they are enumerated here and not invented per step:

| Code | Meaning |
|---|---|
| 0 | Clean shutdown, or a successful `-version` / `-validate-config` / `-dump-openapi` / `-healthcheck` |
| 1 | Unexpected runtime error |
| 2 | Invalid configuration — the message names the offending variable |
| 3 | Migration failure at boot; no listener was bound |

`-version`, `-dump-openapi` and `-healthcheck` short-circuit **before** configuration validation, so
they keep working as later steps tighten what a full boot requires (§9 rule 9).

## 8. Authentication & Authorization

### Provider and rationale

**Single-scope static API keys, read from `NFC_API_KEYS` at boot and compared in middleware on the
`/v1/` subtree. No provider, no database, no user table, no sessions.**

`knowledge/capabilities/auth.md`'s own recommendation table ends at exactly this case: *"There are
no humans, only services → API keys or client-credentials tokens. No session layer at all."* That
is this system. Nobody signs up for a flow collector; a network engineer points Grafana at it and
an SRE `curl`s it during an incident.

**The deliberate deviation — and it is a deviation, named here so nobody "fixes" it back.**
`auth.md`'s schema table specifies a DB-backed `api_key` table (`id, org_id, name, key_hash,
prefix, scopes, last_used_at, revoked_at`) with hashing on write, per-key scopes, and revocation as
a row update. **This blueprint does not build that table.** The keys live in an environment
variable that the operator already manages with the same tooling they use for the database
password.

| What the `api_key` table buys | Why v1 does not need it |
|---|---|
| Per-key scopes | There is exactly one scope. Every `/v1` endpoint is a read over the same data, and §1 lists RBAC beyond one key scope as a Non-Goal |
| Self-service issuance | The issuer and the consumer are the same operations team. Issuance is `openssl rand -hex 32` and an edit to the deployment's environment |
| Revocation without a deploy | Revoking means removing a line from `NFC_API_KEYS` and restarting — a sub-second restart of a process that already tolerates restarts, since UDP ingest is lossy by design and Kafka resumes from its consumer group |
| Hash-at-rest, so a DB leak is not an access leak | There is no row to leak. The keys are in the process environment, which is the same blast radius as `NFC_POSTGRES_DSN`. Storing a hash of a secret that is already sitting next to it in the same env block buys nothing |
| `last_used_at` | The `warn` log on every 401 plus the request-id trail on every 200 already answers "is this key in use" |

**The v2 path, if it is ever needed, is the one `auth.md` describes, unchanged.** The trigger is
written into §1's Non-Goals: *two teams need different views of the same collector*. At that point
the `api_key` table above is added with `key_hash` (SHA-256, never the raw key), `prefix` for
identification in logs, and a `scopes` column; `internal/api/auth.go`'s middleware signature does
not change, only its lookup — it goes from "is this key in the configured set" to "is this key's
hash an unrevoked row, and does its scope admit this route". The middleware is deliberately the
only place that answers that question, so the swap is one file plus a migration.

### Flows

There is no sign-up, no sign-in, no email verification, no password reset, no onboarding, no
session expiry and no account deletion, because there are no accounts. The flows that do exist are
operational, and all four are documented in `docs/runbook.md` (step 12):

**Issuing a key.**
1. Operator runs `openssl rand -hex 32` and gets a 64-character hex string.
2. Operator appends it to the deployment's `NFC_API_KEYS` (comma-separated, no spaces).
3. Operator restarts the collector. Boot re-reads the variable; there is no hot reload in v1 and
   no signal handler that rereads configuration.
4. Operator hands the key to the client out of band. **The key is never printed by the collector,
   never returned by an endpoint, and never written to a log in full.**

**Presenting a key.** Every `/v1/*` request carries `Authorization: Bearer <key>`. No query
parameter is accepted and no custom header is accepted — a key in a URL lands in every access log
and every browser history between the client and the server, which is the one place a secret must
never be.

**Rotating a key.** Add the new key to `NFC_API_KEYS` alongside the old one → restart → move every
client to the new key → remove the old key → restart. The list is comma-separated precisely so that
both keys are valid during the overlap; a single-key variable would make rotation an outage. This
is the procedure `.env.example` states inline next to the variable.

**Revoking a key.** Remove it from `NFC_API_KEYS` and restart. Revocation is immediate on restart
and there is nothing to expire, because nothing is cached and no token was ever minted.

**The failure branches, all of which are the same response.** Missing header, malformed header
(no `Bearer ` prefix), empty key, unknown key, and a key that was valid before the last restart all
produce **401** with the §5 error envelope, `error.code = "unauthorized"`, the request's
`request_id`, and a `WWW-Authenticate: Bearer realm="netflow-collector"` response header. The
message never distinguishes "you sent no key" from "you sent a wrong key" — distinguishing them
tells an attacker which half of the problem they have solved.

**The boot failure branch.** `NFC_API_KEYS` empty while the API is enabled is a configuration
error, not a permissive default: the process exits with code **2** and a message naming
`NFC_API_KEYS`, per §5's exit-code table. An API that falls back to "no key required" when its key
list is empty is how an internal service ends up open, and it fails silently and permanently.

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| `/v1/flows` | A key from `NFC_API_KEYS` in `Authorization: Bearer <key>` | `internal/api/auth.go` — middleware wrapping the `/v1/` subtree, registered in `internal/api/server.go` |
| `/v1/exporters` | Same middleware, same rule — protection is applied to the subtree, never per handler | `internal/api/auth.go` via the `/v1/` subtree registration in `internal/api/server.go` |
| `/healthz` | Unauthenticated | `internal/api/ops.go`, registered outside the `/v1/` subtree |
| `/readyz` | Unauthenticated | `internal/api/ops.go`, registered outside the `/v1/` subtree |
| `/metrics` | Unauthenticated | `internal/api/ops.go`, registered outside the `/v1/` subtree |

**Why the operational endpoints are open.** An orchestrator's liveness probe, a Prometheus scraper
and a container healthcheck are all machine callers that predate any key the operator would hand
them, and a probe that needs a secret is a probe that fails during exactly the incident it exists to
report. These three endpoints are protected at the **network** layer instead: the compose file binds
the HTTP listener to `127.0.0.1:8080`, and a production deployment puts `/v1` behind the operator's
ingress while leaving `/metrics` reachable only from the monitoring network. This is stated as a
residual risk in §20.3 rather than hidden here — `/metrics` does expose exporter counts, ingest
rates and drop rates to anyone who can reach the port.

**Enforcement rule:** authorization is checked server-side on every request. It is checked in one
place — the `/v1/` subtree middleware — and never duplicated into a handler, because two checks
that can disagree are worse than one. `.claude/rules/api.md` states the same rule, so a new `/v1`
route is protected by the act of registering it on that subtree; a route registered anywhere else
is a code-review failure, not a silent hole, because `internal/api/server.go` has exactly one
`/v1/` mount point.

**Comparison is constant-time and exhaustive.** `internal/api/auth.go` loops over **every**
configured key and accumulates the result of `crypto/subtle.ConstantTimeCompare`; it never
`return`s on the first match or the first mismatch. An early return leaks, through response timing,
both which key matched and how far down the list the comparison got. `ConstantTimeCompare` returns
0 for unequal lengths, which does leak key length — accepted, because every issued key is the same
64 hex characters and length therefore carries no information.

**Logging.** A 401 logs at `warn` with the **first six characters** of the presented key and never
the whole value, so an operator can correlate a rejected client without the log becoming a
credential store. A successful request logs no key material at all. `internal/obs/logging.go`
carries `NFC_API_KEYS` and `Authorization` in its redaction list so that a future
configuration-dump or request-dump helper cannot reintroduce the leak.

### Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| Holder of a valid key | `GET /v1/flows`, `GET /v1/exporters` — the full dataset, every exporter, every time range the retention window still holds | Write anything (no `/v1` endpoint mutates), read another tenant's data (there are no tenants), administer keys, reach a debug or admin surface (none exists) |
| Anonymous caller | `GET /healthz`, `GET /readyz`, `GET /metrics` | Everything under `/v1` |

That is the entire authorization model: **there are two roles, and one of them is "has the key".**
No role column, no permission check inside a handler, no client-side guard — there is no client to
guard. Adding a second scope is the v2 change described above and is a Non-Goal for v1.

### Sessions

**NOT APPLICABLE as a stateful concept — the API is stateless and every request is authenticated
independently.** Stated positively so the builder does not go looking for the piece that is
missing:

- **Token type:** none. There is no minted token, no JWT, no refresh token and no token family.
  The bearer credential *is* the long-lived static key.
- **Storage:** the client holds the key however it holds `NFC_POSTGRES_DSN` — an environment
  variable, a Grafana data-source secret, a secrets manager. The server holds it in memory, loaded
  once at boot from `NFC_API_KEYS`.
- **Lifetime:** until the operator removes it from `NFC_API_KEYS` and restarts. No expiry, because
  an expiring credential with no self-service renewal endpoint is an outage with a timer on it.
- **Refresh:** none. Rotation is the procedure above.
- **Cookies:** none are set, so `HttpOnly`, `Secure` and `SameSite` have nothing to apply to.
- **CSRF:** not applicable, and for two independent reasons — the credential is an
  `Authorization` header a browser never attaches automatically, and every `/v1` endpoint is a
  read with no side effects (§5). No CSRF token, no double-submit cookie, no `SameSite` strategy.
- **Session revocation / "sign out all devices":** the closest equivalent is key revocation, which
  is a restart and is documented above.

### Multi-tenancy / row-level isolation

**NOT APPLICABLE — there is no tenant boundary to cross.** Every key sees the whole dataset by
design: the collector belongs to one operations team, and §1 lists multi-tenancy as an explicit
Non-Goal with its revisit trigger. There is no `org_id` column on `exporters` or `flow_records`
(§4), no RLS policy, and no mandatory scope in the data layer — adding a filter that always matches
everything would be a mechanism that teaches the next reader a boundary exists when it does not.

The v2 path is the one thing worth stating, so that the absence is a decision rather than an
oversight: tenancy would land as a scope column on the `api_key` table described above plus an
`exporter_id`-set restriction applied inside `flow.Querier`'s implementations — in the data layer,
never in the handler — because "remember to filter" is not a mechanism.

## 9. BUILD ORDER

**This is the section the whole blueprint exists to produce.** Everything above is context; this is
the instruction set. A builder that follows Section 9 exactly and stops when each gate goes green
ships the project.

### The rules of a step

1. **One sitting per step.** No step here touches more than 5 files or carries more than 6
   acceptance criteria.
2. **Every step carries all four fields:** `Do`, `Done when`, `Verify`, `Checkpoint`. A step missing
   any of them is not a step.
3. **"Done when" conditions are EARS-form and machine-checkable:** **WHEN** `<trigger>`
   **THE SYSTEM SHALL** `<observable response>`. "It looks right" is banned.
4. **`Verify` is literal shell**, run from the project root, and **every line exits 0 when the step
   is correct.** Where the right answer is a failure, the line asserts the specific code
   (`cmd; test $? -eq 2`) or the specific status (`test "$(curl … -w '%{http_code}')" = 401`), never
   a bare command and never `!` alone.
5. **A step is not done until its own verify commands pass** *and* every earlier step's still do.
   Nothing here adds a requirement that retroactively breaks an earlier gate: every `NFC_*` variable
   is defined in step 1 and variables are required only from the step that consumes them, and
   `-version`, `-validate-config`, `-dump-openapi` and `-healthcheck` short-circuit before config
   validation for the same reason.
6. **`Checkpoint` is a literal shell block**, not a sentence: it commits the step's work and tags it
   `step-NN-{slug}`. That tag is the rollback target for the next step —
   `git reset --hard step-{N-1}-…` and retry, never debug forward through a broken checkpoint.
7. **A `Verify` may not assert what its own `Checkpoint` produces.** At `Verify` time the step's
   files are written but untracked and the tree is dirty. Tracked-file assertions live in the
   `Checkpoint` block, after the commit that makes them true.
8. **Never skip ahead.** If a step is blocked, stop and report.

### One step, one unit — the counting rule

> **One Section 9 step = one `tasks.json` task = one task block in an epic file.**

This build has **13 steps**, therefore 13 tasks in `tasks.json` and 13 task blocks across the epic
files — 7 in `epics/01-ingest-core.md` (`E1-T1`…`E1-T7`) and 6 in
`epics/02-serving-and-operations.md` (`E2-T1`…`E2-T6`). With 13 steps and an epic holding 5–9 steps,
exactly 2 epics are legal, which is what the bundle contains. The three views are the same 13 units
seen three ways; never subdivide a step inside an epic.

#### Step 2 — Add NetFlow v5/v9/IPFIX UDP source

**Do**
A `net.ListenPacket` loop on `NFC_NETFLOW_ADDR` with a read buffer of 65535 bytes, handing each
datagram to `decode.go`, which sniffs the wire version (the packet's first 2 bytes) and dispatches
to one of **two separate goflow2/v2 packages** — `decoders/netflowlegacy` for v5 (fixed layout,
`DecodeMessage`/`PacketNetFlowV5`) and `decoders/netflow` for v9/IPFIX (template-driven,
`DecodeMessageVersion`/`NetFlowTemplateSystem`) — before mapping either result to `flow.FlowRecord`.
Keep the template system for v9/IPFIX alive across datagrams and keyed by exporter — a template
arrives once and every later datagram from that exporter depends on it. Set `ReceivedAt` once per
datagram from the collector's clock, truncated to microseconds, and leave `DedupKey` nil: UDP is
append-only here by design, because NetFlow has no retransmission and paying for dedup would cost a
unique-index write on every record to prevent something that does not happen. Never block on the
output channel — `select` on `ctx.Done()` so cancellation is always honoured. The test builds its
own v5 datagram with `encoding/binary` from the wire layout in `epics/01-ingest-core.md`
(*Conventions that bite in this area*); do not paste a capture. Read goflow2's exported surface with
`go doc github.com/netsampler/goflow2/v2/decoders/netflowlegacy` and
`go doc github.com/netsampler/goflow2/v2/decoders/netflow` before mapping either one, rather than
recalling the API.

#### Step 3 — Add bounded ingest pipeline with drop accounting

**Do**
`internal/obs/metrics.go` creates the six instruments once, at package level, over
`prometheus/client_golang`'s default registerer: `netflow_records_ingested_total{source}`,
`netflow_records_dropped_total{reason}`, `netflow_batch_write_duration_seconds{sink}`,
`netflow_batch_write_errors_total{sink}`, `netflow_pipeline_buffer_length`, and
`netflow_record_visibility_lag_seconds`. `pipeline.go` owns a `chan flow.FlowRecord` of capacity
`NFC_PIPELINE_BUFFER`; the ingest side does a non-blocking `select` with a `default` that increments
the drop counter — that `default` branch is the entire backpressure strategy, and it must never be
replaced with a blocking send or a growing slice. The batcher flushes at `NFC_BATCH_SIZE` or after
`NFC_BATCH_INTERVAL`, whichever comes first; `NFC_WORKERS` goroutines take batches and call
`WriteBatch` on every sink **in parallel**, collecting errors per sink rather than aborting the
batch. A slow or failing sink degrades that sink's metrics and nothing else.

Files: `internal/obs/metrics.go` (new) · `internal/pipeline/pipeline.go` (new) ·
`internal/pipeline/pipeline_test.go` (new).

**Done when**
- [ ] WHEN a source offers more records than the bounded channel can hold and every sink is blocked THE SYSTEM SHALL drop the excess, increment `netflow_records_dropped_total{reason="buffer_full"}` once per dropped record, and never block the sending source.
- [ ] WHEN 10000 records are offered to a pipeline whose sink accepts instantly THE SYSTEM SHALL write 10000 records and report `netflow_records_dropped_total` of 0.
- [ ] WHEN pending records reach `NFC_BATCH_SIZE` THE SYSTEM SHALL flush a batch of exactly that size, and WHEN `NFC_BATCH_INTERVAL` elapses with a partial batch THE SYSTEM SHALL flush the partial batch.
- [ ] WHEN two sinks are configured and one returns an error THE SYSTEM SHALL still deliver the batch to the other, increment `netflow_batch_write_errors_total` for the failing sink label, and keep running.
- [ ] WHEN the pipeline's context is cancelled THE SYSTEM SHALL flush the pending partial batch to every sink before returning.
- [ ] WHEN a load of records passes through the pipeline THE SYSTEM SHALL satisfy `ingested_total + dropped_total == offered` with no record unaccounted for.

#### Step 7 — Add Kafka source with dedup on write

**Do**
A franz-go consumer group over `NFC_KAFKA_BROKERS` / `NFC_KAFKA_TOPIC` / `NFC_KAFKA_GROUP`, decoding
one JSON flow record per message — the schema is the *Kafka ingest message schema* in §5. Two rules
decide correctness: `ReceivedAt` comes from the message's `received_at`, falling back to the Kafka
record timestamp, and **never** from the consumer's clock; and `DedupKey` is a 16-byte digest of
`(exporter_addr, first_switched, src_addr, dst_addr, src_port, dst_port, protocol)`. Together they
make a redelivered message collide with itself on `(received_at, dedup_key)` and be discarded by the
sink's conflict-tolerant insert — with no code in any sink that knows Kafka exists. Unknown JSON
fields are ignored; a message that fails to decode increments the decode-error counter, is committed
past, and does not wedge the consumer. The test produces to the compose `redpanda` service and
retries its first metadata fetch for up to 30 s.

Files: `internal/source/kafka/kafka.go` (new) · `internal/source/kafka/kafka_test.go` (new) ·
`internal/app/run.go` (edit: register `kafka` in the source switch).

**Done when**
- [ ] WHEN a JSON flow message is produced to `NFC_KAFKA_TOPIC` THE SYSTEM SHALL decode it and emit one record whose fields equal the message's fields.
- [ ] WHEN a message is decoded THE SYSTEM SHALL set `ReceivedAt` from the message's `received_at` field, falling back to the Kafka record timestamp, and SHALL NOT use the consumer's wall clock.
- [ ] WHEN a message is decoded THE SYSTEM SHALL populate `DedupKey` with a 16-byte digest of `(exporter_addr, first_switched, src_addr, dst_addr, src_port, dst_port, protocol)`.
- [ ] WHEN the same message is delivered twice and written through a backend THE SYSTEM SHALL leave the `flow_records` row count unchanged.
- [ ] WHEN a message fails to decode THE SYSTEM SHALL increment `netflow_packets_decode_errors_total{source="kafka"}`, commit past it, and keep consuming.
- [ ] WHEN the context passed to `Start` is cancelled THE SYSTEM SHALL close the client and return within 5 seconds.

### Accounts to create first

**None. There are no third-party accounts, no signups, no API keys to obtain from a vendor, and no
free-tier limits to plan around.**

This is self-hosted infrastructure software, not a SaaS assembled from managed services. Every
dependency of the build runs locally: TimescaleDB, MariaDB and Redpanda are containers from
`docker-compose.yml`, the storage is local Docker volumes, and the only credential in the whole
system — the API key in `NFC_API_KEYS` — is generated by the operator with `openssl rand -hex 32`
rather than issued by anybody. The container images are pulled from Docker Hub anonymously.

Stated explicitly because the absence is otherwise ambiguous: **the builder needs no logins and
should not create any.** If a step appears to need a vendor account, that is a blueprint defect —
stop and report it (§1's rule on Non-Goals applies here too). Publishing the container image to a
registry is a §12 deployment concern and uses the operator's existing registry credentials; it is
not a build prerequisite and no §9 step pushes an image.

landed (§9 rule 9). The **Required by step** column is therefore not about when the key exists — it
exists from Bootstrap — it is the contract with `internal/config`'s validator about when a **missing
or empty** value becomes fatal. Before that step, the variable is optional or defaulted; from that
step on, an empty value exits 2 naming the variable (§5's exit-code table).

`.env.example` is committed with every key present and every value a working local value or an
obviously fake one (`dev-local-key`). `.env` and `.env.*.local` are gitignored — see the table
below. The binary validates this configuration at boot through `internal/config` and fails loudly
with exit code 2 naming the offending variable; it never falls back to a default for a credential,
and specifically never treats an empty `NFC_API_KEYS` as "no key required" (§8).

**"Required by step" is a contract with §9, not a note.** The validator treats a variable as
required only from the step named above and as optional before it, which is what keeps step 9's
arrival from breaking step 4's `go build` gate. The three conditional variables
(`NFC_POSTGRES_DSN`, `NFC_MARIADB_DSN`, the `NFC_KAFKA_*` trio) are required only when the
corresponding entry appears in `NFC_SINKS` / `NFC_SOURCES`, which is what lets a developer run the
Postgres-only default without a MariaDB or a Redpanda container running.

**Listing a variable here does not load it.** There is no framework in this project doing ambient
`.env` loading, so the mechanism is explicit and lives in one place: `internal/config` walks **up**
from the working directory to find the nearest `.env`, loads it, and **never overwrites a variable
already exported in the shell**. The upward walk is the load-bearing part — `go test
./internal/sink/postgres/...` runs with the working directory set to that package, several levels
below the repository root, and a loader that only checked `./.env` would leave every package-level
test without a DSN. Environment-reading tools that are *not* the binary do not exist here: goose is
driven programmatically from inside the process (§4), so it inherits the already-loaded
configuration rather than reading `.env` itself, and there is no standalone migration CLI, seed
script (§4 states there is none) or test-runner plugin that needs its own loader. `docker compose`
reads the `environment:` blocks written literally into `docker-compose.yml`, not `.env`, which is
why those values are duplicated there and reconciled in §19.6.

## 12. Deployment Strategy

### Hosting

**Self-hosted, on the operator's own infrastructure. There is no PaaS vendor and no hosted tier to
name** — this is infrastructure software the operator runs next to their routers, not a SaaS this
project operates. A collector binds a privileged UDP port, holds a bounded in-memory buffer across
requests, and must sit inside the network that exports to it; every one of those is the shape
`deployment.md` marks incompatible with a request-scoped host.

Two artefacts ship, and nothing else:

1. **A single static binary** — `go build -o bin/collector ./cmd/collector` with `CGO_ENABLED=0`.
2. **A container image** built by the multi-stage `Dockerfile` (step 11):

```dockerfile
FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
ARG VERSION=dev
RUN CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=$VERSION" \
      -o /out/collector ./cmd/collector

FROM gcr.io/distroless/static:nonroot
COPY --from=build /out/collector /usr/local/bin/collector
USER nonroot:nonroot
EXPOSE 8080 2055/udp
ENTRYPOINT ["/usr/local/bin/collector"]
```

- **Build command:**
  `docker build --build-arg VERSION=$(git describe --tags --always --dirty) -t netflow-collector:$(git describe --tags --always --dirty) .`
- **Output:** one layer over `distroless/static` containing one file, `/usr/local/bin/collector` —
  the same path `docker-compose.yml`'s healthcheck invokes, and the string §19.6's cross-artifact
  table reconciles.
- **Runtime setting:** non-root, no shell, read-only root filesystem is safe (the process writes
  nothing to disk), all configuration through `NFC_*` environment variables.
- **Image size target: 10–20 MB**, per the Go track's guidance. `CGO_ENABLED=0` plus
  `-trimpath -ldflags "-s -w"` plus a `static` base is what gets there; a `debian`-based final stage
  or a stray cgo dependency is what breaks it, and step 11's gate measures the size rather than
  trusting the Dockerfile to be right.

There is no preview environment: there is no hosted surface to preview, and a per-PR collector with

### CI/CD

`.github/workflows/ci.yml` (step 12). Stages run in this order, each gating the next — **and this is
the same list §20.1 checks, because a check in the acceptance gate is a check in CI, no exceptions:**

```bash
go build ./...                                                    # 1. compiles
go vet ./...                                                      # 2. stdlib static analysis
go tool golangci-lint run ./...                                   # 3. pinned linter, .golangci.yml v2 schema
go mod tidy -diff                                                 # 4. go.mod/go.sum are exactly what the code needs
go test -race -cover ./...                                        # 5. unit + integration + conformance, race detector on
go run golang.org/x/vuln/cmd/govulncheck@latest ./...             # 6. known-vulnerability scan
docker build --build-arg VERSION=$(git describe --tags --always --dirty) \
  -t netflow-collector:$(git describe --tags --always --dirty) .  # 7. image builds
```

Stage 7 pushes the image only on a tagged commit on `main`. The load test
(`go test -tags=load -run TestPipelineLoad ./internal/pipeline/...`) runs on a **nightly** schedule,
not per-push: it is timing-sensitive, it runs without `-race` on purpose, and a shared CI runner's
noise would make it flap. Its result is recorded in `docs/performance.md`.

Stages 1–6 need Docker available to the job (testcontainers and the compose stack), which is the one
runner requirement `docs/deploy.md` states.

### Release and rollback

- **Versioning:** `git describe --tags --always --dirty`, stamped into the binary at build time
  through the `VERSION` build argument and `-ldflags "-X main.version=$VERSION"`, and readable at
  runtime with `./bin/collector -version`. The image tag is the same string, so a running container's
  `-version` output identifies the image that produced it.
- **Promotion:** tag `main` → CI builds and pushes `netflow-collector:<tag>` → the operator updates
  their tag reference and restarts. A restart is the whole deploy: the process is stateless apart
  from the in-flight buffer, which is bounded and explicitly droppable (§3).
- **Rollback: redeploy the previous image tag.** No state conversion, no coordination. The previous
  binary reads the same schema, because of the migration rule below.
- **Migrations are forward-only.** `Down` blocks exist for local teardown and are **never** the
  production rollback plan (§4). A bad migration is corrected by writing a new migration, not by
  reversing one — expand → migrate → contract, so that release N-1 and release N can both read the
  schema at every intermediate moment. That is precisely what makes "redeploy the previous tag" a
  complete rollback rather than half of one. `docs/runbook.md` carries the procedure.
- **Rollback window:** limited only by how long the operator retains image tags; nothing in the data
  path expires.

### Domain, DNS, TLS

NOT APPLICABLE — the operator deploys this behind their own network, reverse proxy and TLS
termination; this project does not own a public domain and serves plaintext HTTP on an internal
address by design. `docs/deploy.md` records the two consequences the operator must handle: the API is
unencrypted at the process boundary, so it belongs on a trusted network or behind a proxy that
terminates TLS, and the NetFlow UDP listener is unauthenticated by protocol and must not be reachable
from outside the exporter network.

## 13. Testing Strategy

Per `knowledge/capabilities/testing.md`. Tests exist to make §9's "Done when" conditions checkable —
there is no coverage threshold for its own sake. `-cover` runs in CI so the number is visible;
nothing fails on it.

| Layer | Framework | What it covers | Where | Runs |
|---|---|---|---|---|
| Unit | `go test` + `testify/require` | Pipeline batching (size trigger vs age trigger), drop-and-count backpressure and the `ingested + dropped == offered` conservation invariant, NetFlow wire-decode edge cases (truncated datagram, unknown template, v9 template arriving after the data flowset, zero-length flowset), cursor encode/decode, config validation, timestamp microsecond truncation | `internal/pipeline/pipeline_test.go`, `internal/source/netflow/netflow_test.go`, `internal/config/config_test.go`, `internal/obs/obs_test.go` | every commit |
| Integration | `go test` + `testcontainers-go` | Both `flow.Backend` implementations against a **real** database: `WriteBatch` round-trip, keyset pagination boundaries, dedup on a replayed `dedup_key`, `Migrate` idempotence, `Querier` filter semantics. Plus the API layer over a real backend: envelope shape, every error code in §5's table, auth middleware | `internal/sink/postgres/postgres_test.go`, `internal/sink/mariadb/mariadb_test.go`, `internal/sink/sinktest/conformance.go`, `internal/api/api_test.go`, `internal/api/auth_test.go` | every commit |
| E2E | NOT APPLICABLE as a browser E2E framework — this is a headless daemon with no UI (§2). The in-process equivalent is `go test` exercising the full stack | The step-5 vertical slice (a synthetic NetFlow v5 datagram on a UDP socket → pipeline → Postgres sink → `Querier` returns the row) and the step-13 load/soak test (throughput floor plus conservation under forced overload) | `internal/app/e2e_udp_postgres_test.go`, `internal/pipeline/load_test.go` (build tag `load`) | vertical slice every commit; load test nightly and pre-release |

### The load-bearing test

**`internal/sink/sinktest/conformance.go` is the most important test in this project.** It is one
suite, written once, run unmodified against `PostgresSink` and against `MariaDBSink`. The
architecture's central claim — that a storage backend is a `Sink` plus a `Querier` and nothing more —
is true exactly as long as that file compiles against both and needs no branch for either.

Three rules follow, and they are enforced rather than hoped for:

1. **The suite takes a `flow.Backend` and nothing else.** It never imports `internal/sink/postgres` or
   `internal/sink/mariadb`, never accepts a `*pgxpool.Pool` or a `*sql.DB`, and never reads a DSN.
2. **No branch on backend identity.** No `if backend == "mariadb"`, no dialect switch, no skipped
   assertion. If an assertion cannot hold for one backend, the interface is wrong — not the suite
   (`.claude/rules/testing.md`, §19.5).
3. **It is frozen once written.** Step 4 authors it against Postgres; step 6 adds MariaDB and its gate
   **diffs `conformance.go` against its step-4 commit** and requires an empty diff. Making the suite
   pass by editing the suite is the one failure this design cannot survive, so the gate makes it
   impossible to do quietly.

Every future backend — a columnar store, ClickHouse, whatever v2 brings — passes this same file
unmodified or it is not a backend.

### Critical flows to cover E2E

1. **UDP datagram to queryable row.** A synthetic NetFlow v5 datagram is written to the collector's
   UDP socket; within the batch interval the record is returned by `Querier` with every field intact
   and timestamps equal at microsecond precision. This is the whole product in one test — if it
   passes, the pipeline, the decoder, the batcher, the sink and the schema all agree.
2. **Both backends, one suite.** `go test -race ./internal/sink/...` runs `sinktest.Conformance`
   against a live TimescaleDB container and a live MariaDB container in the same run. This is the
   architecture's acceptance test, not a storage detail.
3. **Kafka redelivery is deduplicated on write.** The same message is delivered twice from the topic
   and exactly one row exists afterwards, with `received_at` taken from the **message** and never from
   the consumer's clock — the invariant that makes at-least-once delivery safe here.
4. **The API contract under failure, not only under success.** Missing key → 401 `unauthorized`; `end`
   before `start` → 422 `validation_error` with `details[0].field == "end"`; an undecodable cursor →
   400 `bad_request`; every configured `Querier` failing → 503 `backend_unavailable` with the
   underlying error logged and never in the response body.

### Test data

- **Databases are ephemeral and per-run.** `testcontainers-go` starts a fresh
  `timescale/timescaledb:2.30.1-pg17` and a fresh `mariadb:11.8.9` for the suites that need one, runs
  `Migrate` against it, and tears it down. Tests never share a database, never share mutable state,
  and never depend on execution order — each one creates the rows it asserts on.
- **`docker-compose.yml` (§19.6) is the other provisioning path**, used by
  `docker compose up -d --wait` in §10 Bootstrap for the local loop and by the step-5 vertical slice,
  which points at the host ports the compose file owns (15432 Postgres, 13306 MariaDB, 19092
  Redpanda) through `NFC_POSTGRES_DSN`, `NFC_MARIADB_DSN` and `NFC_KAFKA_BROKERS` in `.env.example`.
  Both files are emitted under `workspace/` and land in the project before step 1 — the integration
  layer requires a real database, so the file that provides one is shipped, not assumed.
- **Flow records are synthesised, never captured.** NetFlow test datagrams are constructed in Go from
  the wire-format field layout (step 2) and from `goflow2`'s own test fixtures. There is no committed
  `.pcap` and no binary blob whose provenance nobody can restate.
- **There is no seed script and no seed command** (§4). A fresh database needs no rows; what a
  developer needs is traffic, and the tests generate it.

### What is deliberately not tested

| Not tested | Why that is a decision, not an omission |
|---|---|
| Real NetFlow traffic from production routers | It is not reproducible, not committable, and would carry live network data into the repo (§14). Synthetic datagrams built from the wire spec cover every field and, unlike a capture, can be made malformed on purpose |
| GeoIP / ASN enrichment | Out of scope for v1 (§1 Non-Goals). There is no code to test |
| The Kafka source under broker failure beyond basic redelivery | Partition rebalance under a killed broker, consumer-group generation churn and offset-commit races are a hardening exercise with a far larger fixture cost than v1 earns. v1 tests exactly one property — a redelivered message produces one row — and **this is recorded as a v2 hardening item in §20.3, not a v1 gate** |
| Browser / UI behaviour | There is no UI (§2, §15) |
| The operator's own ingress, TLS termination and network policy | Outside the artefact this project ships (§12) |
| Sustained multi-day soak | The nightly load test runs for minutes, not days. A true soak belongs to the operator's staging environment and is named in `docs/runbook.md` |

## 14. Security & Secrets

The threat model is stated plainly, because it decides which rows below are real controls and which
are honest deferrals: **this is single-tenant infrastructure software on an operator's internal
network.** There is no public surface, no browser, no cookie, no multi-tenant data boundary, and one
class of caller — the operator's own Grafana and scripts. The controls that matter here are input
validation, SQL safety, key hygiene, and not leaking network data into logs.

| Concern | Control | Implemented in |
|---|---|---|
| Secret storage | **Environment variables only. No secret is ever committed.** `.env.example` is committed with every key present and a non-secret local value (`NFC_API_KEYS=dev-local-key`, DSNs pointing at `127.0.0.1` with the throwaway compose credentials); `.env` is gitignored and created from the example by §10 Bootstrap. In production the operator supplies `NFC_*` through their orchestrator's own secret mechanism | `workspace/.env.example` (§19.6), `workspace/.gitignore` (§19.6), `internal/config/config.go` |
| Secret rotation | `NFC_API_KEYS` is a **comma-separated list** precisely so rotation is zero-downtime: add the new key → restart → move clients → remove the old key → restart. Generate with `openssl rand -hex 32`. Database and broker credentials rotate on the operator's own cadence; the collector reads them only at boot, so rotation is a restart | `internal/api/auth.go`, procedure in `.env.example` and `docs/runbook.md` |
| Input validation | `github.com/go-playground/validator/v10` over the per-operation request struct at **every** API boundary, plus the same library over `config.Config` at boot. An unknown query parameter is a 422 naming it, never silently ignored (§5) — a silently-dropped filter returns a wrong answer that looks right, which on a traffic-analysis tool is the worst possible failure. Flow records from the wire are validated too: a datagram that does not decode is counted and dropped, never partially written | `internal/api/flows.go`, `internal/config/config.go`, `internal/source/netflow/decode.go` |
| Output encoding / XSS | No HTML is ever produced. Every response is `encoding/json` marshalled with `Content-Type: application/json; charset=utf-8` and `X-Content-Type-Options: nosniff`. No template engine is imported, so there is no injection sink to escape | `internal/api/server.go` |
| SQL injection | **Parameterized queries only, in both backends, without exception.** `pgx` uses `$N` placeholders and `CopyFrom` for batch writes; `database/sql` + `go-sql-driver/mysql` uses `?` placeholders. **No SQL string is ever built by concatenation, `fmt.Sprintf`, or interpolation of a request value — including `ORDER BY`, `LIMIT` and the keyset cursor comparison, all of which are fixed statements with bound parameters.** `limit` is clamped to an integer server-side before it reaches any statement. This is a hard rule for both `Sink` implementations and for every backend added later | `internal/sink/postgres/postgres.go`, `internal/sink/mariadb/mariadb.go`, `.claude/rules/flow-contracts.md` (§19.5) |
| AuthN / AuthZ | Static API key from `NFC_API_KEYS`, required on every `/v1/*` route, compared with `crypto/subtle.ConstantTimeCompare` in middleware **before** the handler runs — server-side, on every request, with no client-side counterpart to bypass. There is exactly one scope, so authorization is authentication (§8). `/healthz`, `/readyz` and `/metrics` are deliberately unauthenticated: they carry no flow data, and orchestrators and scrapers need them | `internal/api/auth.go` |
| CSRF | NOT APPLICABLE — there is no browser, no cookie and no ambient credential. Authentication is a bearer header a script sets explicitly, so a cross-site request cannot carry it. A CSRF token on a header-authenticated JSON API protects nothing | — |
| Rate limiting / abuse | **NOT APPLICABLE for v1** — internal tool, single tenant, trusted network, and a caller set of "our own Grafana and our own scripts". The real protection against an expensive query is structural: the `[start, end)` range is mandatory, `limit` is clamped to 1000 server-side, and there is no unbounded scan of `flow_records` from the API, ever (§5). **v2 item: if the API is ever exposed beyond the operator's own network, a per-key limiter is required before that exposure, not after.** Recorded with its trigger in §20.3 | — (trigger in §20.3) |
| Webhook verification | NOT APPLICABLE — no inbound webhooks. The two ingest paths are a UDP listener and a Kafka consumer, neither of which is an HTTP callback. The Kafka path's integrity control is dedup-on-write keyed on `dedup_key` taken from the message, not a signature | — |
| Dependency audit | `go run golang.org/x/vuln/cmd/govulncheck@latest ./...` as a required CI stage on every push and PR — it reports only vulnerabilities in code paths actually reachable from this binary, so a finding is real work rather than noise. `go mod tidy -diff` in the same pipeline keeps `go.mod`/`go.sum` from drifting. Fixed by whoever owns the build; a failing scan blocks the merge | `.github/workflows/ci.yml` (step 12) |
| Security headers | `X-Content-Type-Options: nosniff` and `Cache-Control: no-store` on every API response. **CSP, HSTS, Referrer-Policy and frame options are NOT APPLICABLE** — they are browser directives, nothing here serves HTML, and HSTS in particular would be wrong from a process that deliberately serves plaintext behind the operator's own TLS terminator (§12) | `internal/api/server.go` |
| PII handling | Flow records contain **source and destination IP addresses of the operator's own network traffic**. This system associates them with no name, account or identity, and NetFlow carries no packet payload (§1 Non-Goals). **But an IP address is personally identifying under some jurisdictions' definitions — GDPR's reading in particular treats a dynamic IP as personal data in the hands of a party able to link it to a subscriber — so the honest statement is that this database may hold personal data depending on where and on whose network it runs.** The consequences for this build are concrete: retention is configurable (`NFC_RETENTION_DAYS`, default 30) and enforced by the backend — a TimescaleDB retention policy dropping whole chunks on Postgres, a chunked `DELETE ... WHERE received_at < ?` on a ticker for MariaDB (§4) — and access is all-or-nothing behind one API key. **Setting a lawful retention window and controlling who holds the key is the operator's responsibility; this project ships the mechanism with a default, not a compliance posture.** `docs/runbook.md` (step 12) states this in the operator's own words, including that there is no per-subject deletion path and no way to erase one address's records short of a range delete | `internal/sink/postgres/postgres.go`, `internal/sink/mariadb/mariadb.go`, `docs/runbook.md` |
| Logging hygiene | **The API key is never logged** — not on success, not on a 401, not as a redacted prefix, not inside an error wrapping the request. `internal/obs/logging.go` carries an explicit redaction list covering `NFC_API_KEYS`, `NFC_POSTGRES_DSN` and `NFC_MARIADB_DSN` (DSNs embed a password), applied at config-dump and error-wrap sites. Logs are structured JSON via `slog`. A backend error is logged at `error` with the `request_id` and returned to the client as `backend_unavailable` with no detail — the client learns the request failed, not what the database said. Flow records are **never** logged individually at any level: that would copy the whole dataset, addresses included, into a second store with different retention | `internal/obs/logging.go`, `internal/api/server.go` |

**Hard rules**

- No secret is ever committed, printed in a log, sent to an error tracker, or embedded in a client
  bundle. Anything reaching a caller is public — treat it that way.
- All server-side authorization checks run before the work, not after. The API key middleware wraps
  `/v1/*` at the mux, so a new handler is protected by being registered, not by remembering to check.
- **No SQL string is built by concatenation or interpolation, in any backend, ever.** Parameters are
  bound; identifiers are literals in the source. A backend that needs dynamic SQL to pass
  `sinktest.Conformance` is a backend doing something the `Sink` interface does not permit.
- Third-party webhooks are verified by signature before their body is parsed as trusted — vacuously
  satisfied here, since there are none, and the rule stands for whatever v2 adds.
- Never log a flow record's addresses outside an explicit, off-by-default debug path.

**Regulated data.** This project stores no health, financial or children's data and has no user
accounts. It may, depending on deployment, store **EU personal data** in the form of IP addresses, as
described in the PII row above. The obligations that creates for *this build* are exactly three, and
all three are met: retention must be bounded and configurable (it is — `NFC_RETENTION_DAYS`, enforced
by both backends), the data must not be copied into secondary stores by accident (it is not — flow
records are never logged), and the operator must be told plainly what is stored so they can make
their own lawful-basis and retention decisions (they are — `docs/runbook.md`). Anything further — a
data-processing agreement, a per-subject erasure path, pseudonymisation of addresses at ingest — is
the operator's deployment decision and is explicitly out of v1 scope.

## 16. Observability & Cost

An ingest daemon fails quietly: packets keep arriving, the process keeps running, and the only
evidence that anything is wrong is a counter nobody is watching. So observability here is not
decoration — it is the *only* way to know the product is doing its job. Every signal below is
implemented in `internal/obs` (step 10) and instrumented at its source in `internal/pipeline`
(step 3) and `internal/api` (steps 8–10).

### Instrumentation

| Signal | Tool | What it captures | Who looks at it |
|---|---|---|---|
| Logs | `log/slog` with a JSON handler — `internal/obs/logging.go` | Single-line JSON with `time`, `level`, `msg`, `service`, and a `request_id` on every API line; the redaction list replaces any attribute whose key is a secret (`NFC_API_KEYS`, `authorization`, DSN passwords) with `[redacted]` | SRE / on-call, through the operator's existing log pipeline |
| Errors | The same `slog` stream at `level=error`, plus the process exit codes in §5 | Unhandled errors wrapped with `%w` and logged once at the boundary that handles them; boot failures exit 2 (bad config) or 3 (migration failure) instead of serving traffic | SRE / on-call. **There is no third-party error tracker in v1** — this is self-hosted infrastructure software and the operator already aggregates logs; adding a vendor SDK would be a new egress path out of a box that sits next to routers |
| Metrics | `prometheus/client_golang` behind an OpenTelemetry meter provider — `internal/obs/metrics.go`, `internal/obs/otel.go` — scraped at `GET /metrics` | The six instruments below, plus `netflow_packets_decode_errors_total{source}` | Network engineer and SRE, in Grafana |
| Traces | `go.opentelemetry.io/otel` with the **Prometheus exporter as the v1 default** (`NFC_OTEL_ENABLED=false` ships metrics only, and nothing attempts an outbound connection). Setting `NFC_OTEL_ENABLED=true` with `NFC_OTEL_ENDPOINT` switches to an OTLP exporter | Span per batch write and per API request, so a slow sink can be separated from a slow query | Platform engineer, only when a specific latency question is open |
| Uptime | The operator's orchestrator and/or Prometheus blackbox probe against `/healthz` and `/readyz`; `docker-compose.yml` polls the container's own `-healthcheck` every 5 s | Liveness and readiness, distinctly (see below) | SRE / on-call |

**Why the Prometheus exporter is the v1 default:** an OTLP exporter requires a collector process to
exist before the first metric is useful, and this project ships as one binary an operator drops next
to their routers. Prometheus scraping needs nothing outside the process. Distributed tracing is a
real need for some operators, so the OTLP path is implemented and gated behind
`NFC_OTEL_ENABLED` / `NFC_OTEL_ENDPOINT` rather than omitted — but the default costs no external
dependency and no egress.

### The metrics that matter for this project

Every expression below runs against `/metrics`. The metric names are owned by
`internal/obs/metrics.go` (step 3 creates them; step 10 exposes them) and are the same strings
`docs/runbook.md` uses as section headings — see §19.6's *Cross-artifact value reconciliation*.

| Metric | Target | Alert at |
|---|---|---|
| **Ingest rate** — `rate(netflow_records_ingested_total[1m])` | Sustains the §1 success metric: ≥ 20,000 records/second on one instance without unaccounted loss | `rate(netflow_records_ingested_total[5m]) == 0` for 5 min while `NFC_SOURCES` is non-empty → ingest has stopped (runbook: `## ingest has stopped`) |
| **Drop rate** — `rate(netflow_records_dropped_total{reason="buffer_full"}[5m])` | 0 under normal load. This is the backpressure risk's own signal (§20.2 row 1): the pipeline drops rather than blocks, so a drop is the *only* externally visible symptom | `> 0` sustained for 5 min (runbook: `## netflow_records_dropped_total is climbing`) |
| **Pipeline buffer occupancy** — `netflow_pipeline_buffer_length` | < 50 % of `NFC_PIPELINE_BUFFER` (< 32,768 at the shipped default of 65,536) | ≥ 80 % of `NFC_PIPELINE_BUFFER` (≥ 52,429 at the default) for 5 min — this is the *leading* indicator that fires before drops begin |
| **Batch write latency per sink** — `histogram_quantile(0.95, rate(netflow_batch_write_duration_seconds_bucket[5m]))` by `sink` | p95 < 250 ms per sink at the default `NFC_BATCH_SIZE=2000` | p95 > 500 ms for 10 min on any `sink` label, or p95 doubling week over week (runbook: `## a sink is falling behind`) |
| **Batch write error rate per sink** — `rate(netflow_batch_write_errors_total[5m])` by `sink` | 0. A sink that errors is silently losing a whole batch, not a record | `> 0` sustained for 5 min on any `sink` label |
| **Query visibility lag** — `histogram_quantile(0.95, rate(netflow_record_visibility_lag_seconds_bucket[5m]))` | p95 < 120 s — the §1 freshness success metric, measured as write-completion time minus each record's `received_at` | p95 > 120 s for 10 min |

Six numbers, each of which would make an operator change something: raise `NFC_WORKERS` or
`NFC_BATCH_SIZE`, add a sink replica, widen the buffer, or stop pointing more exporters at this
instance. Nothing here exists to fill a dashboard.

### Health check

Two endpoints, deliberately separate — this is the Go runtime track's own guidance
(`knowledge/runtime-tracks/go.md`, deployment notes) and it is restated in §5's route table:

| Endpoint | What it actually verifies | Who polls it |
|---|---|---|
| `GET /healthz` | The process is alive and its HTTP server can answer. **Nothing else.** It returns 200 even while every backend is down | The orchestrator's liveness probe; the container healthcheck |
| `GET /readyz` | Every configured backend answered a ping inside 2 s. 503 with `error.code` `backend_unavailable` otherwise, while `/healthz` stays 200 | The orchestrator's readiness probe; the operator's load balancer |

Conflating them is the failure this split exists to prevent: if a database blip returns non-200 on
the liveness path, the orchestrator kills a process that was merely *waiting*, the restart drops
in-flight batches, and the restart loop outlives the blip. The container healthcheck in
`docker-compose.yml` runs `/usr/local/bin/collector -healthcheck` rather than `curl`, because the
distroless final image has no shell and no curl — the binary GETs `/healthz` on `NFC_HTTP_ADDR` and
exits 0 or 1.

### Cost model

NOT APPLICABLE in the SaaS-cost-table sense — this is self-hosted infrastructure software with no
per-request vendor billing; the real "cost" is the operator's own compute/storage for the chosen
backends, which scales with retention window and ingest volume, not a metered API.

Stated plainly rather than forced into a table that would be fiction: there is no free tier, no
per-request price, and no usage cliff, because there is no vendor in the request path. The two
quantities an operator actually sizes are:

- **Storage** ≈ (records/second) × (86,400 × `NFC_RETENTION_DAYS`) × (row width after TimescaleDB
  compression). Retention is a policy on the hypertable, not application code (§4), so shrinking the
  bill is a `NFC_RETENTION_DAYS` change and a policy re-run — not a migration.
- **Compute** — one process, flat memory bounded by `NFC_PIPELINE_BUFFER` × record size plus
  `NFC_WORKERS` × `NFC_BATCH_SIZE` in flight. That boundedness is the point of the drop-and-count
  design: the daemon cannot grow its way into an OOM kill under exporter burst.

The one number worth writing down after step 13 is the measured records/second on the operator's own
hardware, which `docs/performance.md` records under `## Measured throughput`, `## Configuration` and
`## Machine`. Everything else about cost is a function of that number and the retention window.

### The workspace copy is guarded, and this is why

§10's Bootstrap lands these files with:

```bash
rsync -a --ignore-existing blueprints/netflow-collector/workspace/ ./
# --ignore-existing: never clobber a file the build has since changed.
# rsync (not `cp -Rn`) because BSD/macOS `cp -n` exits 1 when it skips an existing file, which
# would abort the second Bootstrap run under `set -e` — the exact scenario the guard exists for.
# rsync exits 0 whether it copies or skips, on every platform this build targets.
```

Bootstrap is the first thing a stuck builder re-runs, so a second run must be a no-op on anything
already present. **Files that are deliberately never overwritten on a re-run:** `.env.example`,
`.golangci.yml`, `docker-compose.yml`, `.gitignore`, `CLAUDE.md`, `AGENTS.md` and everything under
`.claude/` — plus `go.mod`, `go.sum` and `.env`, which this directory never contains in the first
place. §20.1 carries the manual gate that proves the re-run exits 0 and changes nothing that matters.

**`.claude/commands/` is never emitted**, in either mode. A slash command only fires when a human
types it and an autonomous builder types nothing; repeatable workflows are §19.4 skills, which
activate on intent.

**Everything here passes the project's own gates.** `workspace/` carries no Go source, so `gofmt` and
`golangci-lint` have nothing to reject; the YAML, JSON and Markdown files are the ones the project
itself ships, and `.golangci.yml` excludes the `blueprints` path in both its `linters` and
`formatters` blocks so the bundle's copy of a root config can never collide with the project's
(§19.6, *bundle-path exclusion*).

#### Resolution convention matrix

**The convention, stated once:** every internal package is imported by its **full module path** —
`github.com/bogie5464/netflow-collector/internal/<pkg>` — with no path aliases, no `pkg/`, and no
relative imports; and every embedded asset is addressed **relative to the directory of the file
carrying the `//go:embed` directive**, which cannot reference a parent directory.

Go has no bundler-versus-runtime split: `go build`, `go test`, `go run` and the compiler inside the
Docker build stage all use the **same** resolver, driven by the same `go.mod`. There is genuinely
nothing to reconcile for the *import path* half of the convention, and the honest way to say that is
to name the command for each context and the setting that makes it work — not to omit the rows.

### 20.1 Global acceptance gate

The project is **done** when every command below exits 0 on a clean checkout, and not before. This is
the same set `.github/workflows/ci.yml` runs (step 11) and the same set every Section 9 step is
measured against.

```bash
go build ./...                                    # expect: exit 0
```

rather than a test count, `no unformatted file` rather than a file count. The two numbers that do
appear — `20000` records/second and HTTP `200`/`401` — are requirements, not counts of this

is a non-zero process exit — `-validate-config` against a bad `NFC_SINKS` — asserts the **specific**

### 20.3 Decision log

| # | Decision | Rejected alternative | Why | Would reverse if |
|---|---|---|---|---|
| 1 | **Go** as the runtime track, single static binary with `CGO_ENABLED=0` | Python — the `data-pipeline-analytics` shape's **default** track | The explicit requirement is high-throughput, low-latency ingest with flat memory in a long-running daemon. A goroutine per connection costs kilobytes, GC pauses stay sub-millisecond at this allocation rate, and one file deploys next to the routers. Python would need multiprocessing to use the cores and would still lose on per-record overhead — and the shape's own file names Go as the alternative for exactly this profile | The project stopped being an ingest daemon and became a batch analytics job, where Python's ecosystem would dominate and throughput would stop mattering |
| 2 | **TimescaleDB/Postgres *and* MariaDB** as the two v1 storage backends | Two Postgres-flavoured options (plain Postgres + Timescale, or Postgres + CockroachDB) — easier, and explicitly rejected by the author | Two backends that share a dialect prove nothing: the interface can stay secretly Postgres-shaped and still pass. Rotation today is: add the new key to `NFC_API_KEYS`, restart, move clients, remove the old one | Two teams need different views of the same collector, or keys must be issued to someone who cannot be trusted with a restart — the §1 multi-tenancy revisit trigger. The upgrade path is additive: the middleware boundary does not move |
| 7 | **Prometheus metrics + OpenTelemetry + `/healthz`/`/readyz`** as the operational model | This shape's default: a `pipeline_run` table in the warehouse, rows written per run, dashboards over SQL | That model assumes a **scheduled batch job** with discrete runs to record. This is a long-running daemon with no runs — a `pipeline_run` row would either never close or be written every second, and asking the database how ingestion is doing fails exactly when the database is the problem. Metrics in-process, scraped over HTTP, survive a backend outage and are what the operator's Grafana already reads | The project grew a genuinely batch-shaped component — a backfill or replay job with discrete runs — which would want a run ledger **in addition to**, not instead of, the metrics |
| 8 | **`net/http` stdlib `ServeMux`** | `chi`, `gin`, `echo` | Since Go 1.22 the stdlib mux does method matching and path wildcards, which covers five endpoints completely. chi would buy nested middleware groups this API does not have; gin/echo would put a non-stdlib `Context` into every handler signature and into the `flow.Querier` call path | The API grew past ~20 routes with genuinely nested middleware groups, or a need for per-route rate limiting that a third-party router implements well |
| 9 | **Hand-written repository methods with `pgx/v5` (`CopyFrom`) and `database/sql`** | `sqlc` codegen, or an ORM (GORM, ent) | Each backend owns a handful of statements — maybe sixty lines of SQL. `sqlc` would add a generate step, a drift gate and a second dialect configuration for that. An ORM would additionally hide the one operation that matters here: the batch-copy fast path. Going through `database/sql` for Postgres would forfeit `CopyFrom` entirely | The query surface grew past a dozen statements per backend, at which point `sqlc` (not an ORM) becomes the cheaper option |
| 10 | **goose migrations, hand-authored, embedded via `//go:embed` and run programmatically at boot** | `goose create` generated files, an external migration CLI in the deploy pipeline, or an ORM's auto-migrate | A single static binary must carry its own schema — an external CLI means a second artifact to ship to the same host. Hand-authoring is required because the schema needs a hypertable conversion and a NULL-distinct unique index that no generator writes. Auto-migrate is banned outright: it reorders and drops without asking | The deployment model moved to a platform with a first-class migration phase separate from the process, where embedding buys nothing |
| 11 | **Cursor (keyset) pagination**, `limit` defaulting to 100 and **clamped** to 1000 | Offset pagination; or returning 422 when `limit` is too large | On an append-only time-series table, `OFFSET` degrades linearly and produces duplicate or skipped rows as new records arrive mid-page — exactly the traffic pattern here. Clamping rather than erroring follows `database.md`'s cap guidance: a Grafana panel asking for 5000 gets 1000 and works, instead of breaking a dashboard on a parameter nobody tuned | A consumer genuinely needed random access to page N — which would mean the query shape changed from "recent flows over a range" to something this API is not |
| 12 | **No rate limiting in v1** | A token bucket per key, or per-IP limits at the edge | The API sits on an internal address behind the operator's ingress, the caller set is the operator's own Grafana and scripts, and the real protection against an expensive query is already enforced: a **mandatory** bounded time range plus the server-side `limit` cap. A limiter would add state and a storage decision to protect against a caller we control | The API is exposed beyond the operating team, or a single client's polling measurably degrades ingest — visible as `netflow_batch_write_duration_seconds` rising in step with query volume |
| 13 | **Operator-run container via Docker Compose**, behind the operator's existing ingress | A PaaS (Fly, Render, Cloud Run) or a serverless runtime | This binds a privileged UDP port, must be a persistent process, and lives close to the routers that export to it. `deployment.md` names the exact anti-pattern being avoided — a long-lived process design on a request-scoped host. Compose also keeps the local dev stack and the deployment shape identical | The operator standardised on Kubernetes, in which case the same image ships with a Deployment plus a `LoadBalancer` service for UDP — the artifact does not change, only its manifest |
| 14 | **Module path `github.com/bogie5464/netflow-collector`** | Waiting for a real organisation name, or a placeholder like `example.com/netflow-collector` | A Go module path must be a real, consistent string from the first `import`; a placeholder would be renamed under every file in the tree later. No GitHub organisation was specified, so the author's namespace is the concrete choice. Renaming is two commands and is documented in the README (step 12) | The project moves to an organisation — then `go mod edit -module github.com/<org>/netflow-collector` plus a find/replace across `cmd/`, `internal/` and `migrations/` |

### 20.4 What to build next

The v2 backlog, ordered by what an operator asks for first. Every item is a row from §1's Non-Goals
table and carries that row's own trigger — nothing here is scope, and nothing here may be built
before §20.1 is green.

1. **Database-import `Source`** — replay historical flow records from an existing nfdump or
   ElastiFlow store into the pipeline. *Trigger:* an operator needs to backfill from an existing
   store. **Why first:** it is the cheapest item on this list and the one that pays the architecture
   back. `Source` is `Start(ctx, chan<- FlowRecord) error` and names no network type precisely so a
   database reader satisfies it unchanged; the `add-flow-source` skill (§19.4) is the procedure, and
   the `DedupKey`/`ReceivedAt` rules already cover replay semantics. Expect one package, one test, and
   a `NFC_SOURCES` entry.
2. **GeoIP / ASN enrichment** — annotate records with country and AS-name at ingest or at query time.
   *Trigger:* ingest is stable and someone asks a question AS numbers alone cannot answer. **Why
   second:** it is the most requested analytical feature and the one users notice. It is second rather
   than first because it changes the latency budget: a per-record lookup sits in the hot path, and it
   needs a maintained data file with a refresh story. Design the lookup as a pipeline stage with its
   own metric before writing it, and consider enrich-on-query as the cheaper first cut.
3. **Horizontal clustering / sharding** — exporter-to-instance assignment, per-shard state, and a
   merge layer in the query path. *Trigger:* a single instance saturates, which the §16 metrics show
   before it hurts (buffer occupancy, then drops). **Why third:** it is the item the §20.2 volume risk
   converts into work, and step 13's measured throughput in `docs/performance.md` is the number that
   decides whether it is needed at all. It is a second architecture, not a feature — do not start it
   on a hunch.
4. **Built-in web dashboard / UI** — *Trigger:* a user demonstrates a query shape Grafana genuinely
   cannot express. **Why fourth:** Grafana over the REST API or straight over TimescaleDB is strictly
   better than anything shipped here until that demonstration exists, and a UI doubles the surface
   area, adds a build toolchain to a single-binary project, and makes §15 real work.
5. **Multi-tenancy / RBAC beyond a single API-key scope** — a key table with issuance, hashing, scopes
   and rotation. *Trigger:* two teams need different views of the same collector. **Why last:** it is
   the only item that changes the data model and the auth boundary together, and §20.3 row 6 already
   describes the additive upgrade path, so deferring it costs nothing today.

**Not on this list, and not "later" either:** alerting/anomaly detection (§1 says *never*, unless
flow-specific detection needs state Prometheus cannot carry — the operator's Alertmanager already
does this) and flow payload capture (§1 says *never* — NetFlow carries no payload, and capturing it
would be a different product with a different privacy posture).
